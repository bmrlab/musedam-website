普通的 `GET /api/product/products?page=...` 列表用於瀏覽，而非同步。首次全量複製和每個增量週期都應使用
`GET /api/product/products?sync=true`。所有請求都需要 `products:read`，並使用與普通商品讀取相同的角色和商品庫可見性規則。

## 週期協議

1. 以 `sync=true` 開始，可選 `pageSize`（默認 20，上限 100），以及可選的商品篩選參數 `search`、`brandId`、`categoryId` 和 `status`。全量同步時省略 `updatedAfter`。增量週期時，將其設置為上一個已完成週期的 `syncedUntil` 字符串，且不改變其精度。
2. 按 `id` 和 `updatedAt` 合併返回的商品，保留較新的版本。
3. 使用 `sync=true&cursor=...` 跟隨 `pagination.nextCursor`，直到其為 null。當所選商品在投影期間變為不可見時，空數據頁仍可能帶有下一頁游標。請繼續跟隨該游標。
4. 將已完成週期的 `syncedUntil` 原樣保存，作為下一個檢查點。不要用最後一個商品的時間戳替代它。

同步分頁的結構如下：

```json
{
  "pageSize": 20,
  "syncedUntil": "2026-10-08T12:00:00.123456Z",
  "nextCursor": null,
  "hasMore": false
}
```

游標是不透明且帶版本的。它保留精確的下界、上界、最後的 `(updatedAt, id)` 位置、頁大小和篩選條件。後續請求可以省略篩選條件、頁大小和
`updatedAfter`；將沿用已保存的值。如果重復提供，它們必須與原始週期一致（下界接受等價的 RFC 3339 偏移量）。更改其中任何一項、在其他 API key 或角色下使用游標、游標數據格式錯誤、重復的同步參數，或提供 `page`，均返回 `422 validation_failed`。更換 key 或角色後請重新開始週期。
`cursor` 和 `updatedAfter` 需要 `sync=true`；不支持的 sync 值也會被拒絕。`sync=false` 使用普通的瀏覽列表。

`updatedAfter` 接受帶時區（`Z` 或數字偏移量）的 RFC 3339 時間戳，小數部分為零到六位。無效的日曆日期、無效的偏移量、超過六位的精度，以及晚於安全上界的下界，均返回 `422 validation_failed`。返回的檢查點和同步商品的 `updatedAt`
值使用 UTC，且恰好包含六位小數。請在存儲中原樣保留這些字符串；JavaScript Date 無法保留其完整精度。

## 交付與併發變更

每個週期讀取 `[updatedAfter, syncedUntil)`，先按 `updatedAt` 再按 `id` 排序，均為升序。下界包含在內，上界不包含在內。恰好位於 `syncedUntil` 的行屬於下一個週期。第一頁根據 PostgreSQL 時鐘減去 30 秒的具名安全窗口來計算上界。之後的每一頁都保留這一精確的上界。

該窗口超過 API 15 秒的寫入事務預算，可將最近未提交的更新排除在當前週期之外。保持打開時間超過安全窗口的事務仍是一項限制。同步為至少一次（at-least-once）：將商品移動到當前游標之後的更新可能導致再次交付。請按 ID 和更新時間合併，並使用原始游標重試失敗的頁。

分頁使用 PostgreSQL 原始微秒值。一個短暫的可重復讀事務會將每個選中的時間戳與其商品快照配對，然後在媒體投影之前關閉。響應會重新檢查 key 權限和商品當前的可見性。已刪除或新變為不可見的選中商品會被省略，而不會導致整頁失敗，且游標仍會越過這些選中的行前進。較早頁面中的刪除不會使後續行偏移出結果。

## 核對移除

`POST /api/product/products/visibility` 只接受以下請求體：

```json
{ "ids": [42, 43] }
```

它接受零到 100 個正整數商品 ID（最大 2147483647），保留輸入順序和重復出現的項。其 `data` 不包含任何商品內容：

```json
[
  { "id": 42, "visibility": "visible" },
  { "id": 43, "visibility": "not_visible" }
]
```

對於僅能查看已發佈商品的角色，草稿、已刪除、屬於其他商品庫以及不存在的 ID 都會得到相同的 `not_visible` 值。可編輯和可管理角色還可以看到草稿。只返回提交的 ID；不存在移除事件流或草稿發現端點。請定期針對集成方已存儲的 ID 調用此接口，例如在每個週期完成之後。無效的請求體、非整數 ID、未知的請求體字段以及超過 100 個的批次，均返回 `422 validation_failed`。
