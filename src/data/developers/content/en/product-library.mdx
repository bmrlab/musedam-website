## Quick start

All 28 Product Library operations use POST `https://open.musedam.cc/api/muse/product-api`. Set `service` to the operation identifier shown below and put all business parameters in a flat JSON body.

1. Obtain a MuseDAM API Key.
2. Ask a Product Library manager to add the key as an API Key Collaborator in **Member settings → Add member** and assign the required role.
3. Call the API from your server with an `Authorization: Bearer <APIKEY>` header.

Authorization uses the key’s team and the collaborator’s current role. Request parameters cannot switch product libraries.

New collaborators have the `view_only` role by default. Choose a role for the operations you need:

| Role | Available operations |
| --- | --- |
| `view_only` | View published products. |
| `usable` | View, share and download published products. |
| `editable` | Create and edit products, access drafts, publish and delete products. |
| `manage` | Manage all resources, including brands, categories, information templates and activity records. |

Each role includes the preceding role’s permissions. Replace resource IDs in the examples with actual IDs.

Replace `your_api_key` with your authorized API Key to query the product list:

```bash
curl --request POST 'https://open.musedam.cc/api/muse/product-api' \
  --header 'Authorization: Bearer your_api_key' \
  --header 'Content-Type: application/json' \
  --data-raw '{
  "service": "listProducts",
  "page": 1,
  "pageSize": 20
}'
```

A successful JSON response has `code: "0"`, `message: "成功"`, `result.success: true`, products in `result.data`, and paging information in `result.pagination`. If the list is empty, check whether the library contains products visible to your role; `view_only` and `usable` can only view published products.

## Requests and responses

Every request uses your own MuseDAM API Key in `Authorization: Bearer <APIKEY>` and `Content-Type: application/json`. All operations use the same public POST URL. Resource IDs, pagination, filters and write fields are JSON body fields, alongside the required `service`.

Successful JSON responses wrap the entire former v1 body in `result`; resource DTOs and business input fields are unchanged. The outer success fields are `code: "0"` and `message: "成功"`. Every failure is exactly `{code, message, result: null, traceId}`, with an existing nonzero numeric string `code` from the [error catalog](#error-catalog). Its specific business `message` includes field names and validation details when applicable. Failures have no nested response fields. HTTP statuses and control headers are unchanged.

| Field | Type | How to read it |
| --- | --- | --- |
| `code` | String | `"0"` on success; a nonzero numeric string on failure. |
| `message` | String | `"成功"` on success; a public error message on failure. Do not branch on its wording. |
| `result` | Object or null | The entire former v1 body on success; always null on failure. |
| `result.success` | Boolean, success only | `true`. |
| `result.data` | Object, array or null, success only | The service's unchanged resource DTO, list or mutation result. |
| `result.code` | Null, success only | Unchanged success field. |
| `result.message` | Null, success only | Unchanged success field. |
| `result.pagination` | Object, when present | Ordinary paging or synchronization metadata. |
| `result.requestId` | String, success only | Server request identifier, also exposed in `X-Request-Id`. |
| `traceId` | String | Correlation ID echoed in JSON and logged; falls back to the server request ID. |

Optionally send `traceId` alongside `service` in the request body. It must be a string of 1–128 characters matching `^[A-Za-z0-9._:-]+$`. A valid value is echoed as outer `traceId` and logged. Missing or invalid values use the server request ID for tracing; an invalid value still fails request validation, rather than being silently accepted. Preserve outer `traceId` and `X-Request-Id` when reporting a failure; `result.requestId` exists only on success. Tracing does not change authorization, HTTP statuses, or control headers.

The response examples use `trace_123` to illustrate a valid optional request `traceId`. If you omit it in a request example, expect the generated server request ID instead. `X-Trace-Id` carries the same correlation value.

Ordinary lists accept `page` and `pageSize` and return `result.pagination`. Its `totalCount` is the total record count; `totalPages` is the total page count. The following fragment shows only `result.pagination`, not a complete response:

| Parameter | Default | Range |
| --- | --- | --- |
| `page` | `1` | Integer starting at `1`. |
| `pageSize` | `20` | Positive integer; values above `100` are capped at `100`. |

```json
{
  "page": 1,
  "pageSize": 20,
  "totalCount": 42,
  "totalPages": 3
}
```

Products and assets can become invisible during a request. A page may therefore contain fewer than `pageSize` records while retaining its original counts. Reading an invisible individual resource returns `404`.

Use [cursor synchronization](#cycle-protocol) to maintain a product copy; ordinary page numbers are for browsing. See each endpoint for filters. Ordinary read services ignore unknown business fields; write services reject unknown business fields. History and synchronization reads use stricter validation.

<details id="error-catalog">
<summary>Request limits and errors</summary>

Request bodies are limited to 1 MiB. Write services reject unknown business fields. Ordinary read services ignore unknown business fields; history and synchronization read services validate them strictly. These rules depend on the service, not the HTTP method.

| Result | Action |
| --- | --- |
| 401 / 403 | Check the key, collaborator role, and resource visibility. |
| 404 | The resource is missing, deleted, or inaccessible; check its ID. |
| 422 `"42201"` | Correct the input using the field details in `message`. |
| 409 `sku_in_use` / `name_in_use` | Change the conflicting SKU or name. Soft-deleted products still reserve their SKU. |
| 409 `"40909"` | The mutation committed. Reconcile its state; do not repeat the mutation. |
| 503 `write_conflict` | The mutation rolled back. Wait according to `Retry-After: 1`, then retry. |
| 413 | Reduce the request body size. |

Use outer `traceId` and `X-Request-Id` for troubleshooting failures.



Outer `code` values are numeric strings. Error names below explain their meaning, not response fields. Use the HTTP status and outer code, not message wording, to choose recovery behavior.

| HTTP status | Outer `code` | Meaning | Action |
| --- | --- | --- | --- |
| 401 | `"40101"` | `invalid_credentials` | Check the API Key and Bearer header. |
| 503 | `"50301"` | `authentication_unavailable` | Credential validation is temporarily unavailable; retry later. |
| 401 | `"40102"` | `key_inactive` | Check whether the API Key is inactive or expired. |
| 403 | `"40301"` | `forbidden` | Check collaborator role and required permissions. |
| 404 | `"40401"` | `not_found` | Check the resource ID and current visibility. |
| 409 | `"40902"` | `sku_in_use` | Choose another SKU; soft-deleted products still reserve their SKU. |
| 409 | `"40903"` | `code_in_use` | Choose another resource code. |
| 409 | `"40904"` | `name_in_use` | Choose another resource name. |
| 409 | `"40905"` | `brand_has_dependents` | Remove or reassign dependent categories and products first. |
| 409 | `"40906"` | `category_has_products` | Remove or reassign dependent products first. |
| 409 | `"40907"` | `default_template_replacement_required` | Provide a replacement default template. |
| 413 | `"41302"` | `payload_too_large` | Reduce the request body to at most 1 MiB. |
| 422 | `"42201"` | `validation_failed` | Correct the input using field details in message. |
| 503 | `"50302"` | `write_conflict` | The mutation rolled back; wait according to Retry-After: 1, then retry. |
| 409 | `"40909"` | `mutation_response_unavailable` | The mutation committed; reconcile its state and do not repeat it. |
| 500 | `"50001"` | `internal_server_error` | Retain traceId and X-Request-Id for troubleshooting; reconcile state before retrying a write. |

Validation failure example (HTTP 422):

```json
{
  "code": "42201",
  "message": "Invalid request fields: name: Required",
  "result": null,
  "traceId": "trace_123"
}
```

Error detail wording is illustrative. An invalid request `traceId` is not echoed and still fails validation; outer `traceId` then uses the server request ID.

Mutation response unavailable example (HTTP 409):

```json
{
  "code": "40909",
  "message": "The mutation completed, but its response is unavailable. Do not repeat the mutation.",
  "result": null,
  "traceId": "trace_123"
}
```

For code `"40909"` (`mutation_response_unavailable`), reconcile the committed mutation instead of creating another resource. Do not repeat the mutation.

</details>

## Categories

<details id="category-rules">
<summary>Category trees and deletion</summary>

Sibling names must be unique, and parents must belong to the same brand. A brand allows at most 10 levels and 5000 nondeleted nodes. `sortOrder` is a zero-based sibling position: omission appends new or moved categories and preserves position for same-parent updates. Renaming or moving updates descendant paths.

Creation adds a direct library-default template binding only when that template has no brand bindings or includes this brand. Otherwise creation still succeeds, with ancestor, brand, then library-default resolution. Deletion soft-deletes the entire subtree; any nondeleted product in it causes `409 category_has_products` without deleting anything.

</details>

## Information templates

<details id="template-groups">
<summary>Groups</summary>

`groups` contains 1–200 groups. A template may have at most 200 fields in total.

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Required for an existing group, 1–128 characters, belonging to this template. Omit for a new group. |
| `name` | string | Required, 1–128 characters. Leading and trailing whitespace is trimmed. |
| `fields` | array | Required. Fields in the group, described below. |

Existing groups keep their stored order; new groups append in the supplied order. Groups do not accept `sortOrder` or `isDefault`. The server assigns the default group, which cannot be deleted.

</details>

<details id="template-fields">
<summary>Fields</summary>

New fields require `key`, `name`, and `type`. Existing fields require `id`. When the type is unchanged, omitted properties retain their values, except for `sortOrder`. Changing `type` migrates `config` for the target type; provide new configuration when required.

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Required for an existing field, 1–128 characters, belonging to this group. Omit for a new field. |
| `key` | string | Required for a new field, 1–64 characters. A unique, valid identifier; cannot change for existing fields. |
| `name` | string | Required for a new field, 1–128 characters. |
| `type` | string | Required for a new field. Supported types appear in the configuration table below. |
| `required` | boolean | Optional. Defaults to `false` for a new field. |
| `placeholder` | string | Optional, up to 255 characters. Omit to preserve an existing value; a new field defaults to `null` in responses. |
| `sortOrder` | integer | Optional, nonnegative, and unique within the group. If omitted, uses the field's array position. |
| `config` | object | Depends on the field type; see below. Defaults to `{}` for a new field, but must still meet that type's configuration requirements. |
| `typeChangeConfirmed` | boolean | Optional. Set to `true` for an allowed type change that requires confirmation. |

Creation seeds three protected fields: name, SKU, and main image. This leaves room for up to 197 custom fields. Custom fields in the first group follow those three fields: their supplied `sortOrder` (or array position when omitted) is increased by 3. Replacement definitions must keep these field IDs, types, required flags, and configurations. Fields cannot move between groups.

New fields must be custom fields and cannot use reserved system keys. `isSystemField` and `systemKey` cannot create or reassign system identities; preserve existing identity on update. If supplied, `systemKey` must be a string: `name`, `sku`, `brand`, `category`, `description`, or `mainImage`. Omit it for custom fields. Unknown group or field properties are rejected.

</details>

<details id="field-configuration">
<summary>Field configuration</summary>

`config` depends on the field's `type`. For example, text fields use `{}`, while currency and choice fields need additional configuration.

| Field type | Configuration |
| --- | --- |
| `text`, `textarea`, `email`, `phone`, `url`, `color`, `date`, `dateRange` | Use `{}`. Other configuration properties are not accepted. |
| `number` | Optional `unit`, a string. |
| `currency` | Required `code` and `symbol` (nonempty strings), and `decimals` (an integer from 0 to 4). |
| `richtext` | Required `mode`, either `html` or `delta`. |
| `select`, `radio`, `checkbox` | Required, nonempty `options` array. Entries follow the table below; `value` must be unique. |
| `image`, `file` | Optional `maxCount` (an integer of at least 1), `maxSizeMB` (a number greater than 0), and `accept` (an array of strings). |

Each `options` entry contains:

| Field | Type | Description |
| --- | --- | --- |
| `value` | string | Required, nonempty. The option's unique value. |
| `label` | string | Required, nonempty. The display label. |
| `sortOrder` | integer | Required, nonnegative. |
| `archived` | boolean | Optional. Whether the option is archived. |

System fields support `customPlaceholder`, an optional string of up to 255 characters. System brand and category fields do not accept custom options. Protected system fields cannot change their configuration.

Empty and system configurations reject unknown properties. Other configuration and option validators strip unknown properties. Download the [OpenAPI JSON](/assets/developers/product-library/openapi.json) for the full machine-readable definition.

</details>

<details id="template-definition">
<summary>Returned template definition</summary>

Template details use `groups`; products use `templateDefinition.groups`. Both contain groups and fields. Products return the version pinned at creation, unchanged by later template edits or deletion. `templateDefinition` may be `null` when no template is assigned.

Each group always returns `id`, `name`, `fields`, and these read-only properties:

| Field | Type | Description |
| --- | --- | --- |
| `isDefault` | boolean | Whether this is the default group. |
| `sortOrder` | integer | The group's order. |

Each field always returns `id`, `key`, `name`, `type`, `required`, `placeholder`, `sortOrder`, `config`, and the following properties. The write-only parameter `typeChangeConfirmed` is not returned.

| Field | Type | Description |
| --- | --- | --- |
| `isSystemField` | boolean | Whether this is a system field. |
| `systemKey` | string or null | System identity: `name`, `sku`, `brand`, `category`, `description`, or `mainImage`. `null` for custom fields. |

`placeholder` may be `null`. Media references in configuration return safe preview information without storage paths or credentials. Reading a product's pinned template definition does not require `templates:read`.

</details>

## Products

<details id="template-pins-and-field-values">
<summary>Pinned templates and custom fields</summary>

Products save a template version at creation. Interpret `templateFields` using `templateDefinition`; later template edits or deletion do not change that version. `updateProduct` cannot change the template. `templateFields` uses pinned field IDs as keys and shallow-merges on update; omitted values remain unchanged. Richtext documents may contain internal nulls.

An explicit `templateId` takes priority. Otherwise a supplied `categoryId` resolves the category, ancestors, brand, then library default. Without a category, only the library default is considered, even when a brand is supplied.

| Field type | Input format |
| --- | --- |
| `number`, `currency` | JSON number |
| `dateRange` | Ordered pair of date strings |
| `checkbox` | Array of option values |
| `image`, `file` | Array of FilePath IDs |
| `richtext` | String in HTML mode; `{ "ops": [...] }` in delta mode |

Drafts may omit required values, but supplied and merged fields must meet type and option rules. Publishing or editing a published product validates the complete product. A write may reference at most 100 media items across all fields, using existing same-library FilePath IDs. Omitted media lists stay unchanged; `[]` clears them. Without `coverAssetId`, the first `imageAssetIds` image becomes the cover.

</details>

<details id="cycle-protocol">
<summary>Synchronization and checkpoints</summary>

1. Start with `"sync": "true"`, omitting `updatedAfter` for a full scan. For an incremental cycle, use the previous completed `result.pagination.syncedUntil`.
2. Merge by product `id` and `updatedAt`, retaining the newer version.
3. Follow `result.pagination.nextCursor` with `"sync": "true", "cursor": "<nextCursor>"` until null, including when `result.data` is empty.
4. Save the completed `result.pagination.syncedUntil` unchanged, not the last product timestamp.

Cursors bind the key, role, library, filters, and page size; keep them unchanged while paging. Start a new cycle after authorization or filter changes, and scan fully when the scope expands. Preserve all six fractional digits in checkpoints and sync `updatedAt`; JavaScript Date loses precision. Each cycle reads current state in `[updatedAfter, syncedUntil)`, with the first request’s server time minus 30 seconds as its upper bound. Longer transactions may still affect completeness; this is not an event stream of every change.


Synchronization returns items in `result.data` and metadata in `result.pagination`: `mode`, `syncedUntil` and `nextCursor`. Copy the returned `result.pagination.nextCursor` into the next request’s `cursor` field; do not rename request fields or wrap business input in `result`.

</details>

<details id="reconciling-removals">
<summary>Removing deleted or invisible products</summary>

Sync does not return deletion events. Periodically send local product IDs to [visibility checking](#operation-checkProductVisibility), removing local copies marked `not_visible`. Visibility does not check business filters such as brand, category, or search. For a filtered replica, periodically reconcile the full filtered result or sync all visible products and filter locally.

</details>

<details id="media-and-expiry">
<summary>Preview and download links</summary>

Use `previewUrl` to display product media. For originals, check `downloadUrl`; preview access does not establish download permission.

| Link | Availability | Maximum service-issued lifetime |
| --- | --- | --- |
| Derived preview | Appropriate viewing permission | 3600 seconds |
| Original-image preview fallback | Images only; may also be returned to `view_only` | 300 seconds |
| `downloadUrl` | Resolvable, visible association; `usable` or higher plus `products:read` and `products:download` | 300 seconds |

Every service-issued link is also bounded by the API key's expiry. Fetch product data again after a link expires; do not persist signed URLs as asset identifiers.

<details id="product-media-fields">
<summary>Which fields do covers, images, and related assets return?</summary>

`cover` is one media object, or null when there is no cover. `images` and `relatedAssets` are arrays of media objects. Custom image/file values may be arrays or null; unset fields may be omitted.

| Field | Type | Description |
| --- | --- | --- |
| `id` | Integer or null | ID returned by asset lookup (FilePath ID), not an AssetObject ID or product-asset association ID |
| `name`, `mimeType` | String or null | File name and MIME type |
| `size` | String or null | Decimal byte count, such as `"2048"`; never a JSON number |
| `width`, `height`, `duration` | Number or null | Media dimensions and duration |
| `previewUrl` | URL or null | Preview for display; null when unavailable |
| `downloadUrl` | URL or null; may be omitted | Original file URL; availability is described above |
| `downloadUrlExpiresAt` | Timestamp or null; may be omitted | Download URL expiry in RFC 3339 format |

</details>

<details>
<summary>How do missing links, legacy media, and external previews behave?</summary>

- Non-image assets only return derived previews. Original PDFs, archives, and documents never serve as preview fallbacks. Library asset lookup and template configuration contain previews only.
- Missing download permission or an unresolved association omits `downloadUrl` and `downloadUrlExpiresAt`. With permission but an unavailable original, those values may be null.
- Stored external DAM thumbnails or previews are returned only to API keys without expiry, after excluding known original URLs. The provider controls their lifetime; short expiry and provider-signature validation are not guaranteed.
- For an API key with `expiresAt`, an external preview whose expiry cannot be verified is null. Signature-like query parameters are not a trusted expiry source.
- Service-issued URLs keep the limits above. Signing failure never falls back to a raw storage URL.

</details>

## Download history

<details id="download-usage">
<summary>About download records</summary>

History includes browser, member, share and existing API key operations across the team. `requested` means accepted, not transferred or saved locally. Product reads, previews and direct access to signed `downloadUrl` links do not create history records. The public product API provides no file-download or export operations; browser, member and share downloads and exports are unchanged.

</details>

<details id="file-snapshot-fields">

A download record's `files` array preserves file details when the operation is first accepted.

| `name` | String | File name at the time of the operation |

</details>

### List team download history

**Endpoint**: https://open.musedam.cc/api/muse/product-api

**Method**: POST

**Description**: Lists records from every browser actor and API key in the current team, newest first by createdAt and id. Optional productId returns complete matching operations; omission selects all team records. Only service, productId, page and pageSize are accepted; unknown fields return 422. The current API key or creator never implicitly narrows the list. Requires manage plus products:history, without products:read.

Required role: manage.

**Request parameters**:

| pageSize | Integer | No | Positive page size, default 20, capped at 100. |
