## Quick start

All 28 Product Library operations use POST `https://open.musedam.cc/api/muse/product-api`. Set `service` to the operation identifier shown below and put all business parameters in a flat JSON body.

1. Obtain a MuseDAM API Key.
2. Ask a Product Library manager to add the key as an API Key Collaborator in **Member settings → Add member** and assign the required role.
3. Call the API from your server with an `Authorization: Bearer <APIKEY>` header.

Permissions follow the key’s settings in "Member Settings" - "Roles & Permissions".

Choose a role for the operations you need:

| Role | Available operations |
| --- | --- |
| `view_only` | View brands, categories, information templates, and published products; check product ID visibility. |
| `usable` | All `view_only` operations, plus obtain signed original `downloadUrl` links when reading products and create product shares (`createProductShare`). |
| `editable` | All `usable` operations, plus query library assets (`listAssets` / `getAsset`), create and edit products, access drafts, publish, return to draft, and soft-delete products. |
| `manage` | Manage all resources, including creating/updating/deleting brands, categories, and information templates, revoking shares, and viewing share/download history. |

Each role includes the preceding role’s permissions. Replace resource IDs in the examples with actual IDs.

Replace `your_api_key` with your authorized API Key to query the product list:

```bash
curl --request POST 'https://open.musedam.cc/api/muse/product-api' \
  --header 'Authorization: Bearer your_api_key' \
  --header 'Content-Type: application/json' \
  --data-raw '{
  "service": "listProducts",
  "page": 1,
  "pageSize": 20
}'
```

A successful response uses HTTP 200 with `code: "0"`, an example `message: "OK"`, `result.success: true`, products in `result.data`, and paging information in `result.pagination`. If the list is empty, check whether the library contains products visible to your role; `view_only` and `usable` can only view published products.

## Requests and responses

All operations use `POST https://open.musedam.cc/api/muse/product-api` with `Authorization: Bearer <APIKEY>` and `Content-Type: application/json`. Put `service` and all business parameters at the top level of the JSON body.

**Success response example**:

```json
{
  "code": "0",
  "message": "OK",
  "result": {
    "success": true,
    "data": {},
    "code": null,
    "message": null,
    "requestId": "request_123"
  },
  "traceId": "trace_123"
}
```

Observed public gateway success and error responses use HTTP 200. Upstream Product Library failures return outer `code: "MB100005"` and `result: null`; invalid credentials return `code: "MO100002"` and `result: null`. The `message` may embed an internal HTTP status and response body, but is diagnostic text, not a stable machine-readable protocol. Preserve the response `traceId`; upstream may replace a submitted `traceId`. Forwarding of `Retry-After` or `X-Request-Id` response headers is not guaranteed.

**Permission-denied gateway response example (HTTP 200; illustrative diagnostic wording)**:

```json
{
  "code": "MB100005",
  "message": "product-library HTTP 403: {\"code\":\"0\",\"result\":{\"success\":false,\"data\":null,\"code\":\"forbidden\",\"message\":\"Insufficient permissions\",\"requestId\":\"request_123\"}}",
  "result": null,
  "traceId": "trace_123"
}
```

| Field | Type | Description |
| --- | --- | --- |
| `code` | String | Public gateway code: `"0"` on success, `"MB100005"` for upstream failures, `"MO100002"` for invalid credentials. |
| `message` | String | Example success wording: `"OK"`. Unstable diagnostic text; do not parse it or branch on it. |
| `result` | Object / null | Business result on success; `null` on gateway errors. |
| `result.success` | Boolean | `true` in public success results; absent on gateway errors. |
| `result.data` | Object / Array | Returned object or array on success. |
| `result.code` | null | `null` on success. [Internal error codes](#error-catalog) are troubleshooting references, not public gateway error fields. |
| `result.message` | null | `null` on success; absent on gateway errors. |
| `result.pagination` | Object | Pagination metadata returned on list and sync endpoints. |
| `result.requestId` | String | Request ID. |
| `traceId` | String | Trace ID. |

List endpoints accept `page` (default `1`) and `pageSize` (default `20`, max `100`) and return pagination counts in `result.pagination`. For continuous product synchronization, use [cursor synchronization](#cycle-protocol).

```json
{
  "page": 1,
  "pageSize": 20,
  "totalCount": 42,
  "totalPages": 3
}
```

<details id="field-formats">
<summary>Field formats and conventions</summary>

| Field | Usage |
| --- | --- |
| Numeric resource IDs | Positive integers up to `2147483647`. |
| Template, group, field, and version IDs | Strings; preserve as received and do not assume UUID format. |
| Asset IDs | Use the `id` returned by `listAssets` / `getAsset`. |
| Category `iconAssetId` | Dedicated category icon asset ID uploaded in the web UI (returned on existing categories). It is distinct from library asset IDs returned by `listAssets` and cannot be uploaded or listed via Open API. |
| `size` | Decimal byte-count string or `null` to avoid precision loss. |
| Dates | RFC 3339 strings or `null`; preserve all 6 fractional digits in synchronization timestamps. |
| Product SKU | Named `spu` in the API. |

Omit optional fields on update to keep existing values; **do not pass `null` for optional request parameters** (the internal error is `422 validation_failed`, wrapped by the public gateway as described above). Only fields explicitly documented as clearable accept `""` or `[]` to clear. See [Media links](#media-and-expiry) for preview and download URL expiry rules.

</details>

<details id="error-catalog">
<summary>Request limits and internal error codes (troubleshooting reference)</summary>

The 401, 403, 404, 409, 413, 422, 500, and 503 statuses in this table and later operation descriptions refer to internal Product Library statuses and `result.code`, not public HTTP statuses or gateway error fields. Use the public error contract above; do not parse internal responses embedded in `message`.

Request bodies are limited to 1 MiB. Write, history, and synchronization services reject unknown fields; ordinary list and detail reads ignore unknown fields.

| HTTP status | `result.code` | Description and action |
| --- | --- | --- |
| 401 | `invalid_credentials` | Invalid or missing API Key; check the `Authorization: Bearer` header. |
| 401 | `key_inactive` | The API Key is inactive or expired. |
| 403 | `forbidden` | Insufficient collaborator role permissions. |
| 404 | `not_found` | Resource does not exist, was deleted, or is not visible to your role. |
| 409 | `sku_in_use` | Product `spu` is already in use (including soft-deleted products). |
| 409 | `code_in_use` | Resource code conflict; retry or use a different code. |
| 409 | `name_in_use` | Sibling category name or template name is already in use. |
| 409 | `brand_has_dependents` | Brand still has live categories or products; remove or move them first. |
| 409 | `category_has_products` | Category subtree still has live products; remove or move them first. |
| 409 | `default_template_replacement_required` | Returned when deleting the library default template without `replacementForLibraryDefault` (if a non-existent, deleted, or self template ID is supplied, `422 validation_failed` is returned). |
| 409 | `mutation_response_unavailable` | The mutation committed (`result.mutationOutcome: "committed"`), but its response is unavailable; reconcile state and do not repeat it. |
| 413 | `payload_too_large` | Request body exceeds 1 MiB. |
| 422 | `validation_failed` | Validation failed; fix the input using the field details in `result.message`. |
| 503 | `authentication_unavailable` | Authentication service is temporarily unavailable; retry later. |
| 503 | `write_conflict` | Write conflict rolled back; wait before retrying. The public gateway does not guarantee forwarding `Retry-After`. |
| 500 | `internal_server_error` | Server error; keep `traceId` and `result.requestId` and reconcile state before retrying writes. |

</details>

## Categories

<details id="category-rules">
<summary>Category trees and deletion</summary>

Sibling names must be unique, and parents must belong to the same brand. A brand allows at most 10 levels and 5000 nondeleted nodes. `sortOrder` is a zero-based sibling position: omission appends new or moved categories and preserves position for same-parent updates. Renaming or moving updates descendant paths.

Creation adds a direct library-default template binding only when that template has no brand bindings or includes this brand. Otherwise creation still succeeds, with ancestor, brand, then library-default resolution. Deletion soft-deletes the entire subtree; any nondeleted product in it causes `409 category_has_products` without deleting anything.

</details>

## Information templates

<details id="template-groups">
<summary>Groups</summary>

`groups` contains 1–200 groups. A template may have at most 200 fields in total.

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Required for an existing group, 1–128 characters, belonging to this template. Omit for a new group. |
| `name` | string | Required, 1–128 characters. Leading and trailing whitespace is trimmed. |
| `fields` | array | Required. Fields in the group, described below. |

Existing groups keep their stored order; new groups append in the supplied order. Groups do not accept `sortOrder` or `isDefault`. The server assigns the default group, which cannot be deleted.

</details>

<details id="template-fields">
<summary>Fields</summary>

New fields require `key`, `name`, and `type`. Existing fields require `id`. When the type is unchanged, omitted properties retain their values, except for `sortOrder`. Changing `type` migrates `config` for the target type; provide new configuration when required.

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Required for an existing field, 1–128 characters, belonging to this group. Omit for a new field. |
| `key` | string | Required for a new field, 1–64 characters. Leading and trailing whitespace is trimmed; must match `^[a-zA-Z0-9_]+$` and be unique across the template; cannot change for existing fields. |
| `name` | string | Required for a new field, 1–128 characters. |
| `type` | string | Required for a new field. Supported types appear in the configuration table below. |
| `required` | boolean | Optional. Defaults to `false` for a new field. |
| `placeholder` | string | Optional, up to 255 characters. Omit to preserve an existing value; a new field defaults to `null` in responses. |
| `sortOrder` | integer | Optional, nonnegative, and unique within the group. If omitted, uses the field's array position. |
| `config` | object | Depends on the field type; see below. Defaults to `{}` for a new field, but must still meet that type's configuration requirements. |
| `typeChangeConfirmed` | boolean | Optional. Set to `true` for an allowed type change that requires confirmation. |

Creation seeds three protected system fields (`name`, `sku`, and `mainImage`), leaving room for up to 197 custom fields. Custom fields in the first group follow those three fields: their supplied `sortOrder` (or array position when omitted) is increased by 3. Replacement definitions (`updateTemplate`) must keep all existing system fields' IDs, `type`, `required`, and `config` unchanged (system field settings cannot be modified via Open API). Fields cannot move between groups.

New fields must be custom fields and cannot use reserved system keys (`name`, `sku`, `brand`, `category`, `description`, `mainImage`). `isSystemField` and `systemKey` cannot create or reassign system identities; preserve existing identity on update. If supplied for an existing system field, `systemKey` must match its stored system key; omit it for custom fields. Unknown group or field properties are rejected.

</details>

<details id="field-configuration">
<summary>Field configuration</summary>

`config` depends on the field's `type`. For example, text fields use `{}`, while currency and choice fields need additional configuration.

| Field type | Configuration |
| --- | --- |
| `text`, `textarea`, `email`, `phone`, `url`, `color`, `date`, `dateRange` | Use `{}`. Other configuration properties are not accepted. |
| `number` | Optional `unit`, a string. |
| `currency` | Required `code` and `symbol` (nonempty strings), and `decimals` (an integer from 0 to 4). |
| `richtext` | Required `mode`, either `html` or `delta`. |
| `select`, `radio`, `checkbox` | Required, nonempty `options` array. Entries follow the table below; `value` must be unique. |
| `image`, `file` | Optional `maxCount` (an integer of at least 1), `maxSizeMB` (a number greater than 0), and `accept` (an array of strings). |

Each `options` entry contains:

| Field | Type | Description |
| --- | --- | --- |
| `value` | string | Required, nonempty. The option's unique value. |
| `label` | string | Required, nonempty. The display label. |
| `sortOrder` | integer | Required, nonnegative. |
| `archived` | boolean | Optional. Whether the option is archived. |

All system fields must preserve their existing `type`, `required`, and `config` when updating a template (`updateTemplate`); modifying system field `config` via Open API is not supported.

Empty and system configurations reject unknown properties. Other configuration and option validators strip unknown properties. Download the [OpenAPI JSON](/assets/developers/product-library/openapi.json) for the full machine-readable definition.

</details>

<details id="template-definition">
<summary>Returned template definition</summary>

Template details use `groups`; products use `templateDefinition.groups`. Both contain groups and fields. Products return the version pinned at creation, unchanged by later template edits or deletion. `templateDefinition` may be `null` when no template is assigned.

Each group always returns `id`, `name`, `fields`, and these read-only properties:

| Field | Type | Description |
| --- | --- | --- |
| `isDefault` | boolean | Whether this is the default group. |
| `sortOrder` | integer | The group's order. |

Each field always returns `id`, `key`, `name`, `type`, `required`, `placeholder`, `sortOrder`, `config`, and the following properties. The write-only parameter `typeChangeConfirmed` is not returned.

| Field | Type | Description |
| --- | --- | --- |
| `isSystemField` | boolean | Whether this is a system field. |
| `systemKey` | string or null | System identity: `name`, `sku`, `brand`, `category`, `description`, or `mainImage`. `null` for custom fields. |

`placeholder` may be `null`. Media references in configuration return safe preview information without storage paths or credentials.

</details>

## Products

<details id="template-pins-and-field-values">
<summary>Pinned templates and custom fields</summary>

Products save a template version at creation. Interpret `templateFields` using `templateDefinition`; later template edits or deletion do not change that version. `updateProduct` cannot change the template. `templateFields` uses pinned custom field IDs (`field.id` where `isSystemField: false`) as keys and shallow-merges on update; omitted values remain unchanged. System fields (`name`, `sku`, `brand`, `category`, `description`, `mainImage`) must be passed via top-level request parameters and are rejected in `templateFields`.

An explicit `templateId` takes priority. Otherwise a supplied `categoryId` resolves the category, ancestors, brand, then library default. Without a category, only the library default is considered, even when a brand is supplied.

| Field type | Input format and validation rules |
| --- | --- |
| `text`, `textarea`, `phone` | String, trimmed when saved. Empty or whitespace-only strings clear to `null`; no phone regex is required. |
| `email` | Valid email string; an empty string cannot clear it. |
| `url` | Valid `http://` or `https://` URL string; an empty string cannot clear it. |
| `color` | Hex color string: `#RGB`, `#RRGGBB`, or `#RRGGBBAA`; an empty string cannot clear it. |
| `number`, `currency` | Finite JSON numbers only, not numeric strings or empty strings. |
| `date` | Valid calendar date `YYYY-MM-DD`, or a valid date-time string beginning with that date and `T`; an empty string cannot clear it. |
| `dateRange` | Exactly two valid date strings as above, `[start, end]`, with `start <= end`; no objects or `[]` clearing. |
| `select`, `radio` | String matching an option `value` in field `config.options`; empty-string clearing is not guaranteed. |
| `checkbox` | Array of strings matching option `value`s in field `config.options`; `[]` clears. |
| `image`, `file` | Array of asset IDs returned by asset queries; `[]` clears. |
| `richtext` | Unchanged string in `html` mode (whitespace is preserved); `{ "ops": [...] }` in `delta` mode, with an array of objects that may contain internal nulls. |

No custom field accepts a root `null` input value. Omit a field to preserve its current value.

Drafts may omit required values, but supplied and merged fields must meet type and option rules. Publishing or editing a published product validates the complete product. A write may reference at most 100 media items across all fields (`coverAssetId`, `imageAssetIds`, `relatedAssetIds`, and all custom `image`/`file` fields), using existing same-library asset IDs (`id` returned by `listAssets`). Omitted media lists stay unchanged; `[]` clears them. Without `coverAssetId`, the first `imageAssetIds` image becomes the cover.

</details>

<details id="cycle-protocol">
<summary>Synchronization and checkpoints</summary>

1. Start with `"sync": "true"`, omitting `updatedAfter` for a full scan. For an incremental cycle, use the previous completed `result.pagination.syncedUntil`.
2. Merge by product `id` and `updatedAt`, retaining the newer version.
3. Follow `result.pagination.nextCursor` with `"sync": "true", "cursor": "<nextCursor>"` until null, including when `result.data` is empty.
4. Save the completed `result.pagination.syncedUntil` unchanged, not the last product timestamp.

Cursors bind the key, role, library, filters, and page size; keep them unchanged while paging. Start a new cycle after authorization or filter changes, and scan fully when the scope expands. Preserve all six fractional digits in checkpoints and sync `updatedAt`; JavaScript Date loses precision. Each cycle reads current state in `[updatedAfter, syncedUntil)`, with the first request’s server time minus 30 seconds as its upper bound. Longer transactions may still affect completeness; this is not an event stream of every change.


Synchronization returns items in `result.data` and metadata in `result.pagination`: `pageSize`, `syncedUntil`, `nextCursor`, and `hasMore`. Copy the returned `result.pagination.nextCursor` into the next request’s `cursor` field; do not rename request fields or wrap business input in `result`.

</details>

<details id="reconciling-removals">
<summary>Removing deleted or invisible products</summary>

Sync does not return deletion events. Periodically send local product IDs to [Reconcile known product IDs](#operation-checkProductVisibility), removing local copies marked `not_visible`. Visibility does not check business filters such as brand, category, or search. For a filtered replica, periodically reconcile the full filtered result or sync all visible products and filter locally.

</details>

<details id="media-and-expiry">
<summary>Preview and download links</summary>

Use `previewUrl` to display product media. For originals, check `downloadUrl`; preview access does not establish download permission.

| Link | Availability | Maximum service-issued lifetime |
| --- | --- | --- |
| Derived preview | Appropriate viewing permission | 3600 seconds |
| Original-image preview fallback | Images only; may also be returned to `view_only` | 300 seconds |
| `downloadUrl` | Resolvable, visible association; `usable`, `editable`, or `manage` role | 300 seconds |

Every service-issued link is also bounded by the API key's expiry. Fetch product data again after a link expires; do not persist signed URLs as asset identifiers.

<details>
<summary>How do missing links, legacy media, and external previews behave?</summary>

- Non-image assets only return derived previews. Original PDFs, archives, and documents never serve as preview fallbacks. Library asset lookup and template configuration contain previews only.
- Missing download permission (`view_only` role) or an unresolved association omits `downloadUrl` and `downloadUrlExpiresAt`. With permission (`usable`, `editable`, or `manage` role) but an unavailable original, those values may be null.
- Stored external DAM thumbnails or previews are returned only to API keys without expiry, after excluding known original URLs. The provider controls their lifetime; short expiry and provider-signature validation are not guaranteed.
- For an API key with `expiresAt`, an external preview whose expiry cannot be verified is null. Signature-like query parameters are not a trusted expiry source.
- Service-issued URLs keep the limits above. Signing failure never falls back to a raw storage URL.

</details>

### Partially update a product

**Endpoint**: https://open.musedam.cc/api/muse/product-api

**Method**: POST

**Description**: Merges top-level scalar/custom fields and replaces submitted media lists. Validates against the product's pinned immutable template version, even when the live template is deleted. Updating a published product keeps it published and validates all required fields and media rules against the resulting state atomically. Changing status (`status`) or switching templates (`templateId` / `templateVersionId`) is not supported here.

Required role: editable or manage.

**Request parameters**:

The business fields below are siblings of `service` in the JSON body. Do not wrap them in `params` or `data`. Omitted fields remain unchanged; **at least one field to update must be provided in addition to `service` and `id`**. Supported empty strings (`""`) and empty arrays (`[]`) clear the corresponding fields. `templateFields` shallow-merges by custom field ID; media arrays replace their slot. If `imageAssetIds` is provided without `coverAssetId`, the first image becomes the cover. Updating a published product keeps it published and validates the full resulting state. `templateId`, `templateVersionId`, and `status` are rejected.

Unknown fields are rejected.

## Download history

<details id="download-usage">
<summary>About download records</summary>

History includes browser, member, share and existing API key operations across the team. `requested` means accepted, not transferred or saved locally. Product reads, previews and direct access to signed `downloadUrl` links do not create history records. The public product API provides no file-download or export operations; browser, member and share downloads and exports are unchanged.

</details>
