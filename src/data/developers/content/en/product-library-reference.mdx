## Find an endpoint

For your first integration, follow the [Quick start](./product-library) to obtain access and make your first request. This page groups endpoints by resource and provides their parameters, requests, and responses.

Base URL: `https://open.musedam.cc/api/product`. Append an endpoint path to call it. Replace `your_api_key` and example resource IDs with your own values.

## Common rules

### Permission rules

Each request checks the key status and its team. Unadded, removed, expired or rejected keys cannot access the API. If authentication is unavailable, the API returns `503 authentication_unavailable`. Permissions come from the collaborator’s current role, not the key creator’s role. Requests cannot change the team, library or actor. Product Library provides no key or collaborator management endpoints.

Permissions are assigned through the collaborator role and cannot be selected separately for an individual key. Each endpoint lists its required role. Removing a collaborator preserves audit records, idempotency records, history, and team-owned shares. Revoke shares separately when needed.

Product write responses include product details even without a read
grant. Their original-download properties still require `products:read` AND
`products:download`. `products:publish` also authorizes editing and deleting an
already published product, in combination with the relevant mutation grant.
A status change does not start an approval workflow or external synchronization.

### Wire format and identifiers

Success: `{ "success": true, "data": ..., "code": null, "message": null,
"requestId": "..." }`. Lists add top-level `pagination`. Errors use
`success: false`, `data: null`, a stable `code`, a safe human-readable `message`,
and the same `requestId`. A validation error may include
`details: [{ "field": "templateFields.<id>", "message": "..." }]`.
Messages are contextual and are not stable identifiers; branch on code/status.
JSON operations and errors use `application/json`. Successful file downloads and
exports return attachments, including JSON exports, rather than a success envelope.
All responses use `Cache-Control: private, no-store` and `X-Request-Id`.

Numeric resource IDs are positive integers no larger than 2147483647.
Template/group/field/version IDs are opaque strings, not necessarily UUIDs.
Media IDs are **FilePath IDs**, not AssetObject IDs or product association IDs.
Category `iconAssetId` is a different identifier, from `CategoryIconAsset`.
A legacy/unresolved product media projection may have `id: null`.
`size` is a decimal **string** (or null) so large byte counts remain exact.
Dates are RFC 3339 strings or explicit null, never integer timestamps. Sync
`updatedAt` and `syncedUntil` use six fractional digits; preserve them verbatim.
SKU is `spu` on the wire. Brand `logoUrl` is accepted under constrained writes
but is omitted from all brand read/write DTOs; no raw icon/logo URL is exposed.

Ordinary lists accept `page` (default 1) and `pageSize` (default 20, capped at
100). They return `pagination: { page, pageSize, totalCount, totalPages }`.
Product and asset pages omit records that become invisible while preparing the response, so a
page can be shorter than `pageSize` while the original count remains unchanged.
Single-item reads still return 404 for invisible records. Valid media references are not truncated.
Categories additionally accept `brandId`; products accept `search`, `brandId`,
`categoryId`, and `status`; assets accept `search` and MIME-prefix `mimeType`.
Brand and template lists have no search filter. Unknown ordinary query
parameters are ignored, but strict JSON bodies reject unknown properties.
Synchronization has its own validation and metadata; see [Synchronization and removals](#synchronization-and-removals).

### Writes, concurrency, and limits

Resource creates return 201 and accept optional `Idempotency-Key` (nonblank,
maximum 255 characters, no ASCII controls). The key is scoped to team, API key,
and create operation for 24 hours. Same canonical input replays the original
scalar result and ETag; changed input returns 409. Signed URLs are reprojected
at response time, never saved as replay credentials. Product replay intersects
original media IDs with currently valid associations in their original slots;
it cannot resurrect deleted/invisible products or retain removed downloads.

Catalog item reads and successful catalog mutations return a strong quoted `ETag`.
`PATCH`, status changes, and `DELETE` accept optional
`If-Match`. Pass the received string unchanged. `*` or a comma-separated list
containing the current strong tag also matches; weak tags do not. A stale tag
returns 412 before writes; omission means last-writer-wins. There is no
`If-None-Match`/304 support. Template fingerprints include the full live group,
field, binding and library-default set, so removal/movement invalidates the tag.
Asset detail tags use the FilePath and linked AssetObject identities and maintained
update timestamps. Changes to persistent metadata change the tag; issuing a fresh
temporary preview signature alone does not.
Sharing, activity history and recorded downloads do not use ETag or If-Match.

| Limit                                    | Value                                          |
| ---------------------------------------- | ---------------------------------------------- |
| Body on every route, including reads     | 1 MiB (1048576 bytes); 413 if exceeded         |
| Ordinary or sync page size               | Default 20, maximum 100 (larger values capped) |
| Total product media references per write | 100, across cover/images/related/custom fields |
| Template definition                      | 200 fields total, 1–200 groups                 |
| Template binding arrays                  | At most 10000 IDs per dimension                |
| Category tree                            | Depth 10, 5000 live nodes per brand            |
| Visibility check                         | 0–100 IDs, duplicates and order retained       |
| Sync cursor                              | Opaque string, maximum 8192 characters         |
| Idempotency retention                    | 24 hours                                       |
| Products per share, download or export   | 1–100                                          |
| Files per original download              | 200                                            |
| Original download size                   | 500 MiB combined                               |

There is no v1 429/rate-limit contract. Known rolled-back write contention returns
`503 write_conflict` with `Retry-After: 1`; see [write conventions](./product-library-write-conventions). No multipart upload, remote
asset import, generic provider synchronization, webhooks or bulk writes are
included. Existing UI behavior remains governed by its own workflow.

Read [write conventions](./product-library-write-conventions), [category rules](./product-library-categories),
[template writes](./product-library-template-writes), and [product writes](./product-library-product-writes)
for detailed validation rules.

### Template versions and field values

A product saves the template version used at creation. Later template edits or deletion do not change that product’s field definitions or values. Read the product’s `templateDefinition` for those field definitions.

An explicit live template takes precedence on creation. When `templateId` is
omitted or null and a non-null `categoryId` is supplied, resolution follows the
category or ancestor binding, then the category's brand binding, then the
library default. When `categoryId` is omitted or null, resolution uses only the
library default, even if `brandId` is supplied. If no template resolves, the
product has no template.
A product with a resolved template pins one immutable version. Template mutations always use `newOnly`; `syncAll` is rejected by the
API. Existing products keep their version and values after edits or soft delete.
Read the product's `templateDefinition` to interpret `templateFields`; current
template-head fields can differ. Ordinary product PATCH cannot switch templates.

Template `groups` is a complete replacement when supplied. Preserve group and
field IDs; fields cannot move between groups. Omitted groups/fields are removed
subject to default/system protections. Omitted `groups` preserves the set.
New fields require key/name/type, and keys must be unique valid identifiers.
Binding arrays replace only their own dimension. When selected brands are
nonempty, selected categories must belong to those brands. Moving bindings or
changing the default affects future resolution, not existing product pins.

`templateFields` PATCH shallow-merges by stable custom field ID; null clears a
field. Drafts skip required-value checks, but still validate types, choices,
and media constraints. Number/currency values are JSON numbers; dateRange is
an ordered pair of date strings; checkbox is an option-value array; image/file
input is a FilePath ID array. Richtext is a string in HTML mode or
`{ "ops": [...] }` in delta mode. Published results must pass full validation.
Field configuration shapes and all input lengths are specified in
[openapi.json](/assets/developers/product-library/openapi.json) and [template writes](./product-library-template-writes).

### Media and expiry

Use `previewUrl` to render media. For images, a short-lived original may be used
as a fallback preview even by `view_only` keys. This does not grant general
original-download access. For non-image assets, only derived previews may be
returned; the original PDF/archive/document is never a preview fallback.
Library asset lookup and template configuration contain previews only.

Product media includes `downloadUrl` and `downloadUrlExpiresAt` only when the
current association is resolvable, visible, and authorized by read+download
under `usable` or higher. Missing permission/unresolved references **omit** the
properties; an authorized but unavailable original may produce null. Do not
infer download authorization from an image preview. Signed derived previews
are capped at 3600 seconds, image-original fallbacks and downloads at 300
seconds, all additionally bounded by key expiry. Fetch fresh product data when
URLs expire; do not persist signed URLs as asset identity.

Stored external DAM thumbnails/previews are returned only for keys without
expiry, after excluding known original URLs. Their lifetime remains controlled
by the third-party provider; no short expiry or provider-signature validation is
promised. For a key with `expiresAt`, an external preview with unverifiable
expiry is `null`. URL query parameters, including signature-shaped parameters,
do not establish a trusted expiry. Service-issued derived previews, original
image fallbacks and downloads retain the caps above and never fall back to raw
storage URLs when signing fails.

### Sharing, recorded downloads, and history

`POST /product-shares` creates a fixed selection of 1–100 published products.
Set `expiresInDays` to 7, 30, 90 or null, provide `allowDownload`, and optionally
set a four-digit `accessCode`. The response includes an absolute recipient URL.
Recipients need no login or API key. Content stays live; unpublished or deleted
products are hidden. Shares belong to the team: creator-key expiry, disablement,
removal or role changes do not revoke them. Managers revoke team shares using
`DELETE /product-shares/{id}`.

`GET /products/{id}/download-assets` returns a flat candidate list with opaque
selection keys and `downloadable`, without raw or preview URLs or business
records. `POST /product-downloads` accepts `kind: "assets"` and optional
`assetKeys` (omission selects all originals). One file returns its original
attachment; multiple files return ZIP. Missing originals remain unavailable.
Use `GET /products/{id}/download-assets/{assetKey}` for a single file, encoding
the key as a path segment. Current authorization applies to every retrieval.

For a business-table export, set `kind: "export"` and `format` to `xlsx`
(default), `csv` or `json`; `assetKeys` is not accepted. `locale` defaults to
`zh-CN` and changes system labels/status, not user-authored labels or values.
`includeAssetUrls` defaults to true. Links target the authenticated single-file
route and require a Bearer header; clicking a spreadsheet link alone cannot send
that header. Keys are never embedded in URLs. Use an explicit product share when
recipients need browser access without API credentials. Product read DTOs remain
the stable machine-field interface for synchronization.

Downloads and exports return `X-Download-Record-Id`; `requested` means accepted,
not completed transfer or local save. Detected preparation/stream failures after
acceptance set `failed`; retries do not reset that status. Keep the optional
`Idempotency-Key` for the same logical request within 24 hours, scoped to team,
API key and operation. Matching retries reuse the first record and snapshots,
but reauthorize and transfer current content; bytes are not cached. POST and
single-file GET have separate scopes. Changed input returns 409. Omission, a new
key, or expiry starts a new operation. This is not permanent deduplication.
Before attachment delivery starts, errors retain their specific code and include
`mutationOutcome` when the business record was committed or replayed. Keep the
original idempotency key when retrying that accepted operation. Product reads,
previews and legacy storage `downloadUrl` consumption remain outside business
download history.

Managers with `products:history` query `GET /product-shares` and
`GET /product-downloads`. Omit `productId` for all team records, or provide one
product ID. Both lists accept `page` and `pageSize`, reject unknown/duplicate
parameters, and return newest-first complete operations with pagination. A
product filter preserves the other products/files in each matching operation.
Browser records and records from other team keys are included; creator/key is
not an implicit filter. Key ID and name snapshots preserve attribution after
key lifecycle changes.

### Synchronization and removals

Use `GET /products?sync=true` for a first full sync and incremental cycles.
Supply the previous completed `syncedUntil` as `updatedAfter`. Read every
`nextCursor`, including when the current data page is empty. The fixed interval
is `[updatedAfter, syncedUntil)`, ordered by `(updatedAt, id)` ascending; the
upper bound is PostgreSQL time minus 30 seconds. Save the checkpoint only after
all pages are durably merged. Deduplicate by ID and full-precision update time.
Do not use page-number browsing as a synchronization protocol.

The opaque cursor binds key, role, library, filters, page size and bounds.
Continuation may contain only `sync=true&cursor=...`; repeated parameters must
match. Duplicate sync parameters, `page`, changed bindings or malformed time
bounds produce 422. Timestamp input accepts a timezone and at most six fraction
digits. Transactions longer than the safety window are an accepted limitation.

Synchronization does not include records for deleted products. Periodically send locally known IDs to
`POST /products/visibility`; remove entries reported `not_visible`. This combines
missing, deleted, foreign and role-hidden records without leaking existence.
See [product synchronization](./product-library-synchronization) for the complete
protocol and [examples](./product-library-examples#synchronize-and-save-a-checkpoint) for a loop.

### Protected template fields and category defaults

Template creation automatically adds protected product name, SKU, and main image
fields to the first group before taking the first version snapshot. These three
fields count toward the 200-field limit, so creation accepts at most 197 custom
fields. Their keys are reserved, and updates must retain their IDs and protected
settings. New categories receive a direct binding to the current library default
template only when it has no brand bindings or includes the category's brand;
this direct binding takes precedence over ancestor bindings. Otherwise, creation
succeeds without a direct binding, and template resolution checks ancestors, then
the brand, then the library default. Deleting a category subtree removes its
direct template bindings atomically.
