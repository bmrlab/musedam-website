## Read before updating

To avoid overwriting another change to a product, brand, category or template:

1. Read the resource and save the response `ETag`, including its quotes.
2. Send that value in `If-Match` when using PATCH, changing status or deleting.
3. If the response is `412 precondition_failed`, read again, reconcile the changes and retry with the new ETag.

`If-Match` is optional. Without it, the last write wins. Shares, history and recorded downloads do not use ETag or If-Match.

All requests use `https://open.musedam.cc/api/product`. Access depends on the current API Key Collaborator role. A team, library, actor or operation allowlist in the request cannot grant additional access.

<details>
<summary>ETag matching and validity</summary>

- Catalog item reads and successful mutations return a strong, quoted ETag. Pass it unchanged; do not generate one yourself.
- `*` or a comma-separated list containing the current strong ETag also matches. Weak tags do not. Stale or weak tags return 412 without changing the resource.
- `If-None-Match` and 304 responses are not supported.
- Template groups, fields, bindings and library defaults all affect the ETag. Removal or movement invalidates the old tag.
- Asset ETags depend on the file-path and linked-asset identities and update timestamps. Persistent metadata changes update the tag; refreshing a temporary preview signature alone does not.

</details>

## Retry an uncertain create

Resource creation returns 201. Add an optional `Idempotency-Key` when you need safe retries:

1. Assign a key to one create operation.
2. If the outcome is uncertain, retry within 24 hours with **the same key and input**.
3. Use a new key to create another resource. Different input under the same key returns `409 idempotency_key_reused`.

Keys are scoped to the team, API key and create operation. Use a nonblank value of at most 255 characters, without ASCII control characters.

<details>
<summary>Can the data returned by a retry change?</summary>

- Matching canonical input replays the first successful non-media result and ETag, even if the resource was later edited.
- Media URLs are issued again after checking current access, visibility and associations. Signed URLs are never saved as replay credentials.
- Products retain only original media IDs whose associations remain valid in their original slots. Later additions are excluded, and removed downloads are not restored.
- A replay cannot restore deleted or currently invisible products.

</details>

## Update only the fields you need

| Request content | Behavior |
| --- | --- |
| Omitted field | Preserves its current value |
| Explicit `null` | Clears only a nullable field |
| Product `templateFields` | Shallow-merges by custom field ID; `null` clears that value |
| Template `groups` | Replaces the full definition; preserve existing group and field IDs, including protected system fields |

Unknown JSON properties are rejected. See [product writes](./product-library-product-writes) and [template writes](./product-library-template-writes) for individual fields.

## Brand write requirements

Brand writes require the `manage` role. Create accepts `name`, `description` and `logoUrl`; PATCH must include at least one of them.

| Field | Requirement |
| --- | --- |
| `name` | Nonempty after trimming, at most 128 characters; duplicates allowed |
| `description` | Nullable, at most 512 characters |
| `logoUrl` | An allowed storage/CDN host and HTTP(S) URL without embedded credentials |

A brand cannot be deleted while a nondeleted category or product references it. Reassign or remove those dependencies first.

<details>
<summary>Brand codes, logos and response fields</summary>

- The server generates `code`, unique within the library. Clients cannot set it. Exhausted code conflicts return `409 code_in_use`.
- Logo query signatures are removed before storage. Writes reference a URL; they do not upload or remotely import an asset.
- Brand responses omit `logoUrl`. They return `id`, `name`, `code`, `description`, `website`, `sortOrder`, `isEnabled`, `createdAt` and `updatedAt`.

</details>

## Check whether a write took effect

Before retrying an error, check the write outcome.

| Response | Next step |
| --- | --- |
| `503 write_conflict` | The write rolled back. Wait for `Retry-After: 1`, then retry with the original create key; reread any stale ETag |
| `409 mutation_response_unavailable` | The write committed or was replayed. Reconcile through an authorized read or the original key to avoid duplicate creation |
| A download or export error with `mutationOutcome` | The business record committed or was replayed. Keep the original key when retrying the accepted operation |

<details>
<summary>Response preparation failures and download status</summary>

If a write takes effect but its response cannot be prepared, it returns `success: false`, `data: null` and `mutationOutcome: committed` (or `replayed`). No ETag or media URL is returned. The write was not rolled back.

Downloads and exports retain their specific preparation or delivery error code. `requested` means the request was accepted, not that transfer finished or a file was saved locally.

</details>

## Investigate a failed request

1. Look up the HTTP status and `code` below. Do not identify error types by the `message` text.
2. For validation failures, inspect `details[].field` and correct the input.
3. Provide `X-Request-Id` or the JSON `requestId` when seeking help. Do not log credentials or signed media URLs.

## Find an error and its next step

Expand the group matching the response status.

<details>
<summary>Authentication and access: 401, 403, 404, 503</summary>

| Status / code | Next step |
| --- | --- |
| 401 `invalid_credentials` | The Bearer key is missing, malformed or unknown. Check the header and key |
| 401 `key_inactive` | The key is disabled, revoked or expired. Use an active key |
| 403 `forbidden` | Check the current collaborator role and permissions for the operation or published state |
| 404 `not_found` | Check the ID and visibility. Missing, deleted, other-library and invisible resources can all produce this error; do not infer existence |
| 503 `authentication_unavailable` | Live authentication is unavailable. Retry later; no protected operation runs for this request |

</details>

<details>
<summary>Input and request size: 413, 422</summary>

| Status / code | Next step |
| --- | --- |
| 413 `payload_too_large` | Reduce the request body to at most 1 MiB (1048576 bytes) |
| 422 `validation_failed` | Check query parameters, body, references and field state; use `details` when provided |

</details>

<details>
<summary>Duplicates and dependencies: 409</summary>

| Code | Next step |
| --- | --- |
| `sku_in_use` | Change the nonempty product `spu` that is already in use |
| `code_in_use` | The generated brand code conflicted. Retry creation |
| `name_in_use` | Choose another template name or sibling category name |
| `brand_has_dependents` | Remove or reassign nondeleted categories and products under the brand |
| `category_has_products` | Resolve nondeleted products in the category subtree first |
| `default_template_replacement_required` | Supply a replacement template ID or explicit `null` |

</details>

<details>
<summary>Retries and write outcomes: 409, 412, 500, 503</summary>

| Status / code | Next step |
| --- | --- |
| 409 `idempotency_key_reused` | Canonical input differs for the same key. Keep the original input for a retry; use a new key for a new operation |
| 409 `mutation_response_unavailable` | The change committed or was replayed. Reconcile before retrying |
| 412 `precondition_failed` | Reread, reconcile and retry with the current ETag |
| 500 `internal_server_error` | Preserve `requestId` for investigation; internal details are not exposed |
| 503 `write_conflict` | The write rolled back. Wait for `Retry-After`, then retry with the original key |

</details>

<details>
<summary>File downloads: 409, 413</summary>

| Status / code | Next step |
| --- | --- |
| 409 `download_unavailable` | The original cannot be prepared. Recheck download-candidate availability |
| 413 `download_too_large` | Reduce the selection to at most 200 files and 500 MiB combined |

</details>

## Request count and size limits

| Applies to | Limit |
| --- | --- |
| Bodies on all routes, including reads | 1 MiB (1048576 bytes); larger bodies return 413 |
| Ordinary or synchronization pages | Default 20, maximum 100; larger values are capped at 100 |
| Idempotency records | Retained for 24 hours |

<details>
<summary>Product, template and category limits</summary>

| Applies to | Limit |
| --- | --- |
| Media references in one product write | 100 total across cover, images, related assets and custom fields |
| Template definition | 200 fields total, 1–200 groups |
| Template binding arrays | At most 10000 IDs per dimension |
| Category tree | Depth 10, at most 5000 nondeleted nodes per brand |
| Visibility check | 0–100 IDs; duplicates and order are preserved |
| Synchronization cursor | Opaque string, at most 8192 characters |

</details>

<details>
<summary>Share, download and export limits</summary>

| Applies to | Limit |
| --- | --- |
| Products per share, download or export | 1–100 |
| Files per original download | At most 200 |
| Original download size | At most 500 MiB combined |

</details>

v1 defines no 429 or rate-limit contract. Write contention uses `503 write_conflict`.

Multipart uploads, remote asset imports, generic provider synchronization, webhooks and bulk writes are not available. UI operations retain their own workflows.
