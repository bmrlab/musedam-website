`GET /api/product/categories` lists live categories, with optional `brandId`,
`page`, and `pageSize` filters. Results are flat so clients can build their own
hierarchy from `id`, `parentId`, and `brandId`. Ordering is stable by brand,
parent, sibling position, and ID. `GET /categories/{id}` returns one live
category and its strong `ETag`. Both endpoints require `categories:read`.
Library scope always comes from the API key; caller-supplied tenant IDs do not
change it. Missing, foreign, and deleted item IDs return `404 not_found`.

`POST /categories`, `PATCH /categories/{id}`, and `DELETE /categories/{id}`
require the `manage` role and the matching create, update or delete permission. Follow [writes and error handling](./product-library-write-conventions): use `If-Match` to check for concurrent changes and `Idempotency-Key` to retry creation safely within 24 hours.

## Fields and tree rules

Create accepts required `brandId` and `name`, plus optional `parentId`,
`sortOrder`, `description`, `iconEmoji`, `iconAssetId`, and `isEnabled`.
PATCH accepts a nonempty subset of those optional fields and `name`.
`brandId` cannot be changed after creation.
Unknown fields, including caller-supplied paths or actor IDs, are rejected.

- Names retain their exact spelling, must contain non-whitespace text, are
  limited to 64 characters, and cannot contain `/`. Exact duplicate sibling
  names return `409 name_in_use`; different parents or brands may reuse names.
- Parents must be live categories in the same brand and library. The brand
  must also belong to the key's library. Cycles, invalid references, more than
  10 category levels, and more than 5000 live nodes per brand return
  `422 validation_failed`.
- `sortOrder` is a zero-based position in the destination sibling group.
  Omission appends a new or moved category; an update within the same parent
  preserves its position. Insertion and movement renumber affected siblings.
  Positions beyond the sibling count return `422 validation_failed`.
- Names and parent changes recompute descendant paths without changing IDs.
  Affected categories record the API operator and an updated timestamp.
- `description`, `iconEmoji`, and `iconAssetId` may be cleared with `null`.
  Emoji text is limited to 16 characters. An icon asset must belong to the
  current library. `isEnabled` defaults to true on create.

On creation, the library default template is explicitly bound to the new
category only if the template has no brand bindings or includes the category's
brand. Otherwise, creation succeeds without an explicit category binding;
template resolution still checks ancestors, then the brand, then the library
default.

Responses contain `id`, `brandId`, `parentId`, `name`, `pathKey`, `description`,
`iconEmoji`, `iconAssetId`, `sortOrder`, `isEnabled`, `createdAt`, and `updatedAt`.
`pathKey` is server-owned and starts with `/`. No icon storage URLs, internal
actor relations, or library IDs are exposed or saved in replay snapshots.

## Delete a category and its children

Deleting a category also deletes its child categories. If any category in that subtree contains a nondeleted product, the API returns `409 category_has_products` and leaves every category unchanged.

Deletion is a soft delete: names, parent IDs, brand IDs and historical product relationships are preserved. New categories can reuse the original paths, and the remaining sibling categories are reordered. Product content and status do not change; assets, templates and brands are not deleted. Deleted categories no longer appear in reads and cannot be assigned to products.
