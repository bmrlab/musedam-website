## Approval Open API

- **Production base URL**: `https://open.musedam.cc/api/muse`
- **Approval path**: `/approval-api`
- **Full endpoint**: `POST https://open.musedam.cc/api/muse/approval-api`
- **Availability**: This API is available only after purchasing and enabling the **Approval Center extension module**.

## Request conventions

- Method: `POST`
- `Content-Type`: `application/json`
- Body must be valid JSON
- Use `service` to select the capability
- Include header: `Authorization: Bearer your_api_key`

Supported `service` values:

- `subscriptionQuery`
- `subscriptionChange`
- `listTemplates`
- `createApproval`
- `taskStatusQuery`

## Unified response

```json
{
  "code": "0",
  "message": "success",
  "result": {},
  "traceId": "trace_xxx"
}
```

Common error codes:

- `400`: invalid payload
- `401`: authentication failed
- `403`: permission denied
- `404`: resource not found
- `500`: internal error

## listTemplates

**Path**: `/approval-api`

**Request parameters**:

| Field | Type | Required | Description |
|-|-|-|-|
| service | String | Yes | Fixed value: `listTemplates` |

**Response (`result`)**: an array of templates.

| Field | Type | Description |
|-|-|-|
| id | String | Template ID |
| name | String | Template name |
| description | String | Template description |
| enabled | Boolean | Whether the template is enabled |
| usageCount | Number | Number of uses |
| autoImportEnabled | Boolean | Whether auto-import is enabled |
| targetFolder | Object \| null | Target folder for auto-import |
| workflow | Array | Approval workflow node definitions |

Request:

```json
{
  "service": "listTemplates"
}
```

`result` is an array of templates with fields such as:
`id`, `name`, `description`, `enabled`, `usageCount`, `autoImportEnabled`, `targetFolder`, `workflow`.

**curl**:

```bash
curl --location --request POST 'https://open.musedam.cc/api/muse/approval-api' \
--header 'Authorization: Bearer your_api_key' \
--header 'Content-Type: application/json' \
--data-raw '{
    "service": "listTemplates"
}'
```

|-|-|-|-|

### Callback payload specification

After `subscriptionChange` with `operation = ADD` succeeds, approval state changes are posted to your `callbackUrl`.

#### Callback request basics

- Method: `POST`
- `Content-Type`: `application/json`

Callback body:

```json
{
  "eventId": "evt_xxx",
  "eventType": "APPROVAL",
  "eventTime": "1760258885000",
  "payload": {
    "eventName": "TASK_APPROVED",
    "orgId": "233",
    "taskId": "9527",
    "taskStatus": "APPROVED"
  }
}
```

Field notes:

| Field | Type | Description |
|-|-|-|
| eventId | String | Unique event id (recommended idempotency key) |
| eventType | String | Always `APPROVAL` |
| eventTime | String | Millisecond timestamp string |
| payload | Object | Business payload |

#### Common payload fields

Every callback `payload` contains at least:

| Field | Type | Description |
|-|-|-|
| eventName | String | Event name |
| orgId | String | Organization ID (system populated) |
| taskId | String | Approval task ID |
| taskStatus | String | `PROCESSING` / `APPROVED` / `TIMEOUT` |

#### Full event set

| eventName | Trigger |
|-|-|
| NODE_STARTED | Triggered when a node starts (first node, normal transition, or resubmit transition) |
| APPROVER_SUBMITTED | Triggered when an approver submits a decision (can happen multiple times in one node) |
| NODE_COMPLETED | Triggered when a node is completed (approved/rejected) |
| NODE_TRANSFERRED | Triggered when flow transfers to another node (normal, resubmit, timeout transfer) |
| SUBMITTER_RESUBMITTED | Triggered when submitter resubmits assets in resubmit step |
| TASK_APPROVED | Triggered when the task reaches final approved status |
| NODE_TIMEOUT | Triggered when a node times out (timeout transfer or pending reassignment) |

#### Field definitions

##### `payload.node`

| Field | Type | Description |
|-|-|-|
| nodeId | String | Node ID (always present) |
| nodeOrder | Number | Node order (present in some events) |
| nodeRole | String | `normal` / `resubmit_submitter` / `resubmit_approver` (event-specific) |
| nodeStatus | String | Common values: `pending` / `processing` / `approved` / `rejected` / `timeout_transferred` / `re_assigned` |
| signMode | String | `and` / `or` (event-specific) |
| approverCount | Number | Approver count (event-specific) |
| approvers | Array | Approver results on `NODE_COMPLETED`; item fields: `id`, `name`, `status` |
| startedAt | String | Node start time (ISO) |
| completedAt | String | Node completion time (ISO) |
| timeoutHours | Number | Timeout threshold in hours (timeout events) |

##### `payload.approver` (`APPROVER_SUBMITTED`)

| Field | Type | Description |
|-|-|-|
| id | String | Approver user ID |
| name | String | Approver name |
| decision | String | `approved` / `rejected` |
| comment | String | Approval comment |
| submittedAt | String | Submitted time (ISO) |

##### `payload.submitter` (`SUBMITTER_RESUBMITTED`)

| Field | Type | Description |
|-|-|-|
| id | String | Submitter user ID |
| name | String | Submitter name |
| comment | String | Resubmission comment |
| submittedAt | String | Submitted time (ISO) |

##### `payload.timeout`

| Field | Type | Description |
|-|-|-|
| transferTo | Object \| null | Timeout transfer target; when present: `{ "id": "...", "name": "..." }`, otherwise `null` |

##### `payload.latestAssets` (`SUBMITTER_RESUBMITTED`)

| Field | Type | Description |
|-|-|-|
| assetId | String | Asset ID |
| filePathId | String | File path ID |
| version | Number | Asset version |
| oldStorePath | String | Previous storage path |
| newStorePath | String | New storage path |
| updatedAt | String | Updated time (ISO) |

##### `payload.transferReason` (`NODE_TRANSFERRED`)

| Enum | Description |
|-|-|
| NEXT_NODE | Normal transition to the next approval node |
| RESUBMIT_SUBMITTER | Transition to submitter resubmission node |
| RESUBMIT_APPROVER | Transition to approver re-review node after resubmission |
| TIMEOUT_TRANSFER | Transition after timeout transfer |

#### Event sequence (key flows)

Delivery is at-least-once. Use `eventId` for idempotent processing.

##### Normal pass (multi-node)

1. `NODE_STARTED` (first node)
2. `APPROVER_SUBMITTED` (may repeat for each approver)
3. `NODE_COMPLETED`
4. If next node exists: `NODE_TRANSFERRED` -> `NODE_STARTED`
5. Repeat 2-4 until final node is complete
6. `TASK_APPROVED`

##### Rejected then resubmitted

1. `APPROVER_SUBMITTED` (`decision = rejected`)
2. `NODE_COMPLETED` (`nodeStatus = rejected`)
3. `NODE_TRANSFERRED` (`transferReason = RESUBMIT_SUBMITTER`)
4. `NODE_STARTED` (`nodeRole = resubmit_submitter`)
5. `SUBMITTER_RESUBMITTED`
6. `NODE_COMPLETED` (resubmission node)
7. `NODE_TRANSFERRED` (`transferReason = RESUBMIT_APPROVER`)
8. `NODE_STARTED` (re-review node)
9. Back to normal approval flow (`APPROVER_SUBMITTED` ...)

##### Timeout transfer / no transfer

1. Node timeout triggers `NODE_TIMEOUT` (`taskStatus = TIMEOUT`)
2. If timeout transfer target exists: `NODE_TRANSFERRED` (`transferReason = TIMEOUT_TRANSFER`) and task returns to `PROCESSING`
3. If no transfer target: only `NODE_TIMEOUT` (commonly `nodeStatus = re_assigned`) until manual follow-up
