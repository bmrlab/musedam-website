Ordinary `GET /api/product/products?page=...` listings are for browsing, not
synchronization. Use `GET /api/product/products?sync=true` for both the first full
copy and every incremental cycle. All requests require `products:read` and use
the same role and library visibility rules as ordinary product reads.

## Synchronization steps

1. Start with `sync=true`, optional `pageSize` (default 20, capped at 100), and
   optional product filters `search`, `brandId`, `categoryId`, and `status`.
   Omit `updatedAfter` for a full sync. For an incremental cycle, set it to the
   previous completed cycle's `syncedUntil` string without changing its precision.
2. Merge returned products by `id` and `updatedAt`, keeping the newer version.
3. Follow `pagination.nextCursor` with `sync=true&cursor=...` until it is null.
   An empty data page can still have a next cursor when selected products became
   invisible while preparing the response. Continue following that cursor.
4. Save the completed cycle's `syncedUntil` unchanged as the next checkpoint.
   Do not substitute the final product's timestamp.

Sync pagination has this shape:

```json
{
  "pageSize": 20,
  "syncedUntil": "2026-10-08T12:00:00.123456Z",
  "nextCursor": null,
  "hasMore": false
}
```

The cursor is opaque and versioned. It retains the exact lower bound, upper bound,
last `(updatedAt, id)` position, page size, and filters. A subsequent request may
omit filters, page size, and `updatedAfter`; the saved values apply. If repeated,
they must match the original cycle (equivalent RFC 3339 offsets are accepted for
the lower bound). Changing any of them, using a cursor with another API key or
role, malformed cursor data, duplicate sync parameters, or supplying `page`
returns `422 validation_failed`.
`cursor` and `updatedAfter` require `sync=true`; unsupported sync values are also
rejected. `sync=false` uses the ordinary browsing list.

<details>
<summary>What changes when a key, role, or filter changes?</summary>

- Discard the old `cursor` and start a new cycle.
- If permissions or filters expand the synchronization scope, or the library changes, omit `updatedAfter` and perform a full synchronization. Reconcile the local copy so older products that were previously excluded are not missed.
- When only replacing a key with equivalent access to the same library, role, and filters, reuse the last completed cycle's `syncedUntil`; a full synchronization is not required.

</details>

`updatedAfter` accepts RFC 3339 timestamps with a timezone (`Z` or numeric offset)
and zero to six fractional digits. Invalid calendar dates, invalid offsets,
precision beyond six digits, and a lower bound later than the safe upper bound
return `422 validation_failed`. Returned checkpoints and sync product `updatedAt`
values use UTC with exactly six fractional digits. Preserve those strings in
storage; JavaScript Date cannot retain their full precision.

## Handle updates during synchronization

Each cycle reads `[updatedAfter, syncedUntil)`, ordered by `updatedAt` and then `id`, both ascending. The lower bound is inclusive and the upper bound exclusive. An update exactly at `syncedUntil` belongs to the next cycle. The first page sets the upper bound to the server time minus 30 seconds; every later page uses the same bound.

The 30-second window excludes recent updates that have not yet committed. Transactions lasting longer than this window can still affect synchronization completeness.

Synchronization reads the current product state; it does not provide a record of every historical change. Products may be returned more than once. Merge by ID and update time, and retry a failed page with its original cursor.

Sync timestamps retain microsecond precision. Each response rechecks key permissions and current product visibility. Deleted or newly invisible products are omitted without failing the whole page, and the cursor still advances. Deleting products from earlier pages does not cause later products to be skipped.

## Handle deleted or invisible products

`POST /api/product/products/visibility` accepts only this body:

```json
{ "ids": [42, 43] }
```

It accepts zero to 100 positive integer product IDs (maximum 2147483647), retaining
input order and duplicate occurrences. Its `data` contains no product content:

```json
[
  { "id": 42, "visibility": "visible" },
  { "id": 43, "visibility": "not_visible" }
]
```

For published-only roles, draft, deleted, foreign, and missing IDs all receive the
same `not_visible` value. Editable and manageable roles may also see drafts. Only
submitted IDs are returned; there is no removal feed or draft discovery endpoint.
Call this periodically for IDs already stored by the integration, for example
after each completed cycle. Invalid bodies, noninteger IDs, unknown body fields,
and batches over 100 return `422 validation_failed`.

When an ID is `not_visible`, remove the corresponding product from local storage.

<details>
<summary>How do I reconcile a copy filtered by brand or category?</summary>

`visibility` checks whether a product is still accessible, not whether it matches `search`, `brandId`, `categoryId`, or `status`. A product that leaves the filtered result can still be `visible`.

To maintain a filtered copy, synchronize all products visible to the key and filter them locally. Alternatively, periodically read the complete filtered result and reconcile it with the local copy, removing products that no longer match.

</details>
